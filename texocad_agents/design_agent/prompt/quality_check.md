Quality check contract:
- Treat successful `build_design` output as the usable design artifact boundary: it creates the revision, export, and default `iso` preview that the frontend can show immediately.
- Inspect the default `iso` preview returned by `build_design` against the user's request and any reference images or PDF pages already read with `read_attachment` before making final visual-confidence claims.
- For small parameter edits, primitive/simple geometry, or designs where the relevant features are clearly visible in `iso`, the default preview is enough; do not call extra previews just to be thorough.
- During visual inspection, explicitly check assembly integrity: parts that should touch must actually meet, stacked or mounted features must have visible support, holes/cutouts must be in the intended bodies, and no visible component should be floating, hanging in space, separated by an unintended gap, or only barely intersecting where a firm joint is expected.
- Treat floating/unsupported geometry, accidental gaps, misaligned mating faces, detached decorative elements, and bracket/leg/handle features that do not visibly connect to the main body as likely build defects even if the script executed successfully.
- For objects where basic real-world physics matters unless the user explicitly asks for a decorative, exploded, suspended, or impossible form, check physical plausibility: the model should have a credible support path to the ground or mounting surface, a stable stance or intentional fixture, reasonable center-of-mass placement, and no load-bearing feature that is visibly too thin, disconnected, or unsupported for its apparent role.
- Pay extra attention to physics for furniture, stands, shelves, holders, brackets, hooks, mounts, containers with handles, articulated mechanisms, vehicles, lamps, hanging objects, and anything described as carrying, supporting, balancing, gripping, rolling, folding, or moving.
- Do not overrule explicit user intent: if the user asks for a floating display piece, conceptual cutaway, exploded assembly, magic/sci-fi object, intentionally unstable pose, or purely aesthetic mockup, preserve that intent while still checking that the visible geometry matches it.
- Call `preview_design` when the `iso` preview is unclear, when checking a reference image, hidden or side-specific feature, assembly orientation, asymmetric geometry, attachment/contact between parts, underside/support geometry, physics plausibility, or any other visually risky requirement.
- Choose the most useful additional `view` for the design: `top`, `bottom`, `front`, `back`, `left`, or `right`. Use an orthographic view when a reference image or requested feature is best judged from that side.
- Prefer the view that exposes the suspected connection or support path. For example, use `bottom` or a low oblique custom camera to verify feet, brackets, hanging parts, or underside attachments; use side views to confirm vertical alignment and contact; use `top` for footprint, spacing, and centered mounting.
- If no predefined view shows the relevant features clearly, pass a custom `camera` vector such as `[80, -120, 60]`. Only pass a custom `up` vector when the default `[0, 0, 1]` would make the view ambiguous.
- Check major shape, proportions, orientation, missing visible features, obvious reference mismatch, assembly integrity, and visible physical plausibility. This is not dimensional proof, but it must catch clearly detached, floating, unsupported, or physically implausible components.
- If the quality check reveals a likely mismatch, update the same script and call `build_design` again to create a corrected revision.
- Ask a clarifying question only when correctness depends on subjective preference, ambiguous physical intent, or an ambiguous requirement; do not ask users whether they want visual verification as a routine post-build step.
- In the final response, keep success concise while separating build success from quality confidence: state the revision number and, when useful, add one short clause for `iso` check, extra checked view, physics caveat, or needed user clarification.
- Do not claim visual verification or physics plausibility passed unless `build_design` or `preview_design` returned an image and you inspected it.
